OpenAI Builder Lab 仓库 Wiki

本文基于本地固定提交 e87f060e4e86d599ee54bdc7b752484944278f85（initial commit，2025-01-31）生成。仓库是一个旅行助理教学项目，包含 starting_point 和五个相互独立、逐步增强的挑战快照。默认运行路径是每个快照内的 Next.js 前端及其 Route Handlers；同级 Flask 服务是可选替代后端，不会被前端自动启用。

1. 仓库用途与边界

项目以 “Wanderlust Concierge” 为业务外壳，演示如何从静态占位回复逐步构建具备以下能力的 AI 助理：

  • 基于 OpenAI Chat Completions 的多轮文本对话。
  • 由模型发起函数调用，再由应用执行地点搜索和行程规划。
  • 通过 OpenAI Realtime API、WebRTC 和浏览器麦克风实现语音会话。
  • 通过 SSE 将文本增量和工具参数增量实时推送到浏览器。

仓库根说明见 README.md。六个目录是教程阶段快照，不是一个 monorepo 中互相调用的六个服务。选择某个阶段时，应在该目录内部独立安装和运行。

3. 核心组件

3.1 页面与视觉壳

各阶段的 Main 都只负责将 Assistant 居中放入全屏页面。RootLayout 加载本地 Geist Sans/Mono 字体、全局 CSS 和页面元数据。challenge1 至 challenge4 的标题是 “Wanderlust Concierge”，challenge5 改为 “Conversational Assistant / Structured Outputs demo”，但其业务提示词仍是旅行助理。

相关源码：challenge5/app/page.tsx、challenge5/app/layout.tsx。

3.2 Assistant 与 Chat

Assistant 是 UI 到领域逻辑的入口：

  1. 忽略纯空白输入。
  2. 将同一用户文本转换为两种表示：UI 的 Item 和 OpenAI SDK 的 ChatCompletionMessageParam。
  3. 分别写入 chatMessages 与 conversationItems。
  4. 调用 handleTurn 或最终阶段的 processMessages。

Chat 根据 Item.type 选择 Message 或 ToolCall 渲染；消息变化时滚动到底部；Enter 发送、Shift+Enter 换行。challenge1 至 challenge4 接收 loading 并显示加载项，challenge5 移除了该状态，以增量消息本身呈现进度。

Message 使用 react-markdown 渲染文本；ToolCall 展示工具名称、解析中的参数和最终 JSON 输出。

3.3 双视图会话状态

useConversationStore 使用 Zustand 保存两组数组：

状态 面向对象 内容
chatMessages: Item[] UI 初始欢迎语、用户/助理消息、可视化工具调用
conversationItems: ChatCompletionMessageParam[] 模型 API 用户、助理、tool 消息及 tool_call_id

初始欢迎语只进入 chatMessages，不会发送给模型。每次模型请求都由编排器在 conversationItems 前动态插入 SYSTEM_PROMPT，因此系统提示词也不持久化在 store 中。

flowchart LR Input[用户输入] --> UIItem[Item] Input --> APIItem[ChatCompletionMessageParam] UIItem --> ChatState[chatMessages] APIItem --> ConversationState[conversationItems] SystemPrompt[SYSTEM_PROMPT] --> Request[模型请求] ConversationState --> Request ModelReply[模型输出] --> ChatState ModelReply --> ConversationState ToolResult[工具结果] --> ConversationState

3.4 对话编排器

非流式阶段使用 handleTurn：

  • 读取 Zustand 当前快照。
  • 构造 [system, ...conversationItems]。
  • 调用 /api/get_response。
  • 若助理消息含 tool_calls，执行第一个工具、追加 role: tool 结果并递归进入下一轮。
  • 若没有工具调用，才把最终助理消息加入可见聊天区。

最终阶段使用 processMessages，将 SSE 事件分成三类：

事件 来源 客户端动作
assistant_delta 模型文本 delta 累加助理文本并更新两组状态
function_arguments_delta 工具调用参数 delta 用 partial-json 解析不完整 JSON，实时更新工具卡片和 tool_calls
function_arguments_done finish_reason === "tool_calls" 调用工具、追加 tool 消息，再次执行 processMessages

3.5 工具层

工具层同时包含“给模型看的声明”和“应用真正执行的分派逻辑”。两端名称与参数结构必须同步。

search_location

  • 参数：location: string、search_query: string。
  • Chat Completions 工具定义启用 strict: true 且禁止额外字段。
  • Next.js 实现调用 serpapi.getJson，固定 engine: google、limit: 5，返回 organic_results。
  • 从 challenge2 开始可用。

plan_itinerary

  • 参数：stops 数组，每项包含 location、duration、type、participants。
  • Next.js 实现将 stops 序列化为用户消息，并使用独立的 ITINERARY_PROMPT 调用 o1。
  • 从 challenge3 开始可用。

工具定义与实现见 challenge5/lib/tools.ts，服务端实现见 search_location 和 create_itinerary。

3.6 Next.js Route Handlers

接口 方法 输入 输出 阶段
/api/get_response POST { messages } 普通 JSON 助理消息；challenge5 为 SSE 全部阶段
/api/search_location POST { location, search_query } SerpAPI organic_results challenge2+
/api/create_itinerary POST { stops } { itinerary } challenge3+
/api/session GET 无 Realtime session 上游响应体 challenge4+

这些路由把长期密钥保留在服务端。除 Realtime 的临时 token 外，浏览器不会直接获得 OPENAI_API_KEY 或 SERPAPI_API_KEY。

3.7 可选 Flask 后端

每个阶段都有 python-backend/app.py。其功能随挑战同步演进：

  • /：健康提示文本。
  • /get_response：调用 Chat Completions；起始阶段仍返回固定消息。
  • /search_location：从 challenge2 开始调用 SerpAPI。
  • /plan_itinerary：从 challenge3 开始调用 o1。

Flask 启用了全局 CORS，并以 debug=True、端口 8000 启动。源码注释明确指出生产环境应关闭 debug。前端切换方式不是配置开关，而是把 fetch('/api/...') 手工替换为 fetch('http://localhost:8000/...')。

3.8 Realtime 语音模式

VoiceMode 的设计流程是：

  1. 从 /api/session 获取临时 client_secret。
  2. 创建 RTCPeerConnection，申请麦克风并添加音轨。
  3. 创建 oai-events DataChannel。
  4. 将本地 SDP offer 直接 POST 到 OpenAI Realtime endpoint。
  5. 应用远端 SDP answer，并通过 ontrack 播放模型音频。
  6. DataChannel 打开后发送 session.update；challenge5 同时下发 REALTIME_TOOLS。
sequenceDiagram participant U as 用户浏览器 participant S as Next /api/session participant O as OpenAI Realtime participant T as /api/search_location U->>S: GET /api/session S->>O: POST /v1/realtime/sessions O-->>S: session + client_secret S-->>U: 透传 JSON U->>U: 获取麦克风并创建 SDP offer U->>O: POST SDP + 临时 token O-->>U: SDP answer U->>O: DataChannel session.update O-->>U: 音频轨与事件 U-->>T: 设计上执行 search_location T-->>U: 搜索结果 U->>O: function_call_output + response.create

上图最后四步是源码意图；当前 challenge5 的事件提取条件存在实现缺陷，详见“异常与边界行为”。

4. 主要执行流程

4.1 普通文本与工具循环（Challenge 2-4）

sequenceDiagram participant U as 用户 participant A as Assistant participant Z as Zustand participant R as /api/get_response participant M as OpenAI participant H as handleTool participant X as 工具 API U->>A: 提交文本 A->>Z: 写入 UI 与 API 两份用户消息 A->>R: system + conversationItems R->>M: Chat Completions + tools M-->>R: assistant message R-->>A: JSON A->>Z: 写入 assistant conversation item alt 包含 tool_calls A->>H: 第一个工具名和 arguments H->>X: POST 工具参数 X-->>H: JSON 结果 H-->>A: 工具结果 A->>Z: 追加 role=tool A->>R: 递归发起下一轮 else 最终文本 A->>Z: 写入可见助理消息 end

工具调用消息在非流式阶段不会作为 FunctionCallItem 加入 chatMessages，因此 UI 通常只看到最终回答；工具卡片类型虽已定义，但主要在 challenge5 的流式路径中被实际填充。

4.2 SSE 流式文本与工具调用（Challenge 5）

flowchart TD A[POST messages] --> B[OpenAI streaming completion] B --> C{delta 类型} C -->|content| D[发送 assistant_delta] C -->|tool_calls| E[累计首个工具参数] E --> F[发送 function_arguments_delta] C -->|finish_reason tool_calls| G[发送 function_arguments_done] D --> H[浏览器增量更新消息] F --> I[partial-json 解析并更新工具卡片] G --> J[handleTool] J --> K[追加 tool 结果] K --> L[递归请求模型生成后续回答]

7. 异常、限制与边界行为

以下结论均可由固定提交中的实际控制流直接确认。

7.1 通用限制

  • 输入校验有限：路由直接解构 request.json()；没有 Zod 校验、大小限制或统一 400 响应。缺失字段通常会向下游传递 undefined，或在访问键时抛错。
  • 只处理首个工具调用：非流式编排器和 challenge5 流式路由都使用 tool_calls[0]，不支持同一模型回合中的并行多工具调用。
  • 无最大轮次：工具完成后递归调用编排器。若模型持续请求工具，没有轮次、成本或超时上限。
  • 状态采用原地修改：编排器对从 Zustand 取得的数组执行 push 或修改末项，再复制触发更新。并发发送或多个异步事件可能基于旧快照相互覆盖。
  • 敏感内容日志：多个路由和客户端会记录完整 messages、工具参数或响应；部署前应评估个人旅行信息和密钥相关日志策略。
  • 工具错误未标准化：handleTool 不检查 response.ok，500 JSON 会被当作普通工具输出交回模型；未知工具名返回 undefined。

7.2 Challenge 5 文本流限制

  • handleTurn 在非 2xx 响应时只记录错误但不返回，随后仍对 response.body! 建立 reader；若服务端返回普通 JSON 错误体，SSE 解析不会产生可见错误消息。
  • TextDecoder.decode(value) 未设置流式解码选项；多字节字符若刚好跨 chunk 边界，存在解码异常风险。
  • onMessage 声明为同步回调且调用处未 await，但传入的是异步函数。工具执行和递归回合不在 handleTurn 的完成语义内，可能形成时序竞争或未捕获拒绝。
  • 服务端和客户端各维护一份 functionArguments，且均按单一调用设计；多个交错工具调用会混合状态。
  • processMessages 已把工具参数解析成对象后传给 handleTool；search_location 接受对象，但 plan_itinerary 又执行 JSON.parse(parameters)，因此最终阶段的行程工具会对对象进行 JSON 解析并抛出类型错误。对比 assistant.ts 与 tools.ts。

7.3 Realtime 语音限制

  • startSession 在网络、令牌、麦克风或 SDP 任一步骤前就把 isSessionStarted 设为 true；catch 中未复位。首次启动失败后，再次点击会进入 startSession，但内部条件阻止重试。
  • 获取到的 MediaStream 没有写入 audioStream；stopSession 的显式 track.stop() 分支因此不会执行。tracks 虽收集 sender，也没有用于清理。
  • DataChannel 消息处理先判断 event.type === 'conversation.item.created'，随后令 output = event，再判断 output.type === 'function_call'。同一个 type 不可能同时等于两者，因此当前 challenge5 的 Realtime 工具处理分支不可达。
  • /api/session 无论 OpenAI 上游状态如何都构造 status: 200，客户端又直接读取 session.client_secret.value；上游错误会变成后续属性访问异常，而不是清晰的 HTTP 错误。
  • 麦克风访问依赖浏览器权限和安全上下文；拒绝权限会进入通用 catch，仅写控制台。

7.4 Python 后端限制

  • Flask 路由没有统一异常处理；缺少 JSON 字段、API 密钥或 organic_results 时由 Flask 返回默认错误页。
  • CORS(app) 对全部来源开放，适合教学本地环境，不是收敛后的生产策略。
  • debug=True 会启用调试模式，源码注释已经要求生产关闭。
  • Python 后端没有 Realtime session 端点，也没有实现 challenge5 的 SSE 协议，因此不能完整替代最终阶段的 Next.js 后端。

  • 对 /api/get_response mock OpenAI SDK，覆盖普通文本、工具调用、流错误和多工具调用。
  • 对 processMessages 使用分块 SSE fixture，覆盖 JSON 跨 chunk、UTF-8 跨 chunk 和异步工具完成顺序。
  • 对 handleTool 覆盖对象/字符串参数、未知工具、非 2xx 和无 organic_results。
  • 对 Realtime 使用伪造 RTCDataChannel 事件，验证事件载荷提取、失败重试和音轨释放。
  • 用浏览器测试覆盖 Enter、Shift+Enter、空白输入、连续点击发送和麦克风权限拒绝。

9. 依赖与版本

前端核心技术栈来自各阶段的 package.json：Next.js 14.2.11、React 18、OpenAI JS 4.61.0、Zustand 5、Tailwind CSS 3、partial-json、serpapi（challenge2+）、React Markdown 和语法高亮组件。challenge5 还保留 Recharts、Radix Slot 和 class-variance-authority 等 UI 依赖，但当前业务入口未使用全部组件。

Python 依赖由各阶段的 requirements.txt 固定，核心包括 Flask 3.1.0、OpenAI Python 1.60.0、Flask-Cors、python-dotenv，以及从 challenge2 开始加入的 google_search_results。

cn(...inputs) 先用 clsx 组合条件类名，再用 tailwind-merge 解决冲突，是 UI 基础组件共享的样式合并函数，见 lib/utils.ts。
