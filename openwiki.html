Next.js API 路由与 Python 后端对照

本文档对比 Wanderlust Concierge 项目中两套可互换的后端实现：Next.js 内建 API 路由（位于 frontend/app/api/**/route.ts）与 Python Flask 后端（位于 python-backend/app.py）。两者都向 OpenAI 聊天补全和 SerpAPI 转发请求，并为聊天机器人提供工具调用。它们面向同一套前端，是二选一的关系（不是叠加层），开发时可通过修改前端注释掉的行来切换。

两条后端选择路径

前端不直接调用 OpenAI 或 SerpAPI，而是由后端代理。切换后端只需改变一个 fetch URL：把 /api/<name>（Next.js 路由）换成 http://localhost:8000/<name>（Flask，运行于 8000 端口）。

flowchart TD UI["React 前端组件"] --> TURN["lib/assistant.ts handleTurn"] UI --> TOOL["lib/tools.ts handleTool"] TURN -->|"fetch 默认"| R1["/api/get_response (Next.js, SSE 流式)"] TURN -->|"fetch 注释切换"| P1["/get_response (Flask, 8000 端口)"] TOOL -->|"search_location 默认"| R2["/api/search_location (serpapi getJson)"] TOOL -->|"search_location 注释切换"| P2["/search_location (GoogleSearch)"] TOOL -->|"plan_itinerary 默认"| R3["/api/create_itinerary (model o1)"] TOOL -->|"plan_itinerary 注释切换"| P3["/plan_itinerary (model o1)"] VOICE["components/voice-mode.tsx"] -->|"fetch"| R4["/api/session (Realtime ephemeral token)"] R1 --> O1["OpenAI chat completions stream"] P1 --> O1 R2 --> S["SerpAPI Google engine"] P2 --> S R3 --> O2["OpenAI chat completions (o1)"] P3 --> O2 R4 --> OR["POST api.openai.com/v1/realtime/sessions"]

图：前端通过 fetch 在 Next.js API 路由（默认）与 Flask 后端（注释切换）之间的选择路径。

后端选择点出现在两个前端文件中，以注释形式标注 Python 替代方案：

  • lib/assistant.ts 的 handleTurn 默认 fetch('/api/get_response')，旁边注释了 fetch('http://localhost:8000/get_response')。
  • lib/tools.ts 的 handleTool 默认 fetch('/api/search_location') 与 fetch('/api/create_itinerary')，旁边注释了 http://localhost:8000/search_location 与 http://localhost:8000/plan_itinerary。

因此文本聊天（assistant 组件）依赖 get_response 路径，工具调用（search_location、plan_itinerary）走 tools.ts 路径，语音模式（voice-mode 组件）只走 /api/session。

Next.js API 路由

四个路由均为 app/api/<name>/route.ts 导出的 HTTP handler，由 Next.js 在服务端运行，扮演把浏览器请求转发给 OpenAI / SerpAPI 的代理，避免把 API 密钥暴露给客户端。

/api/get_response —— 流式对话

POST /api/get_response 接收 { messages }（OpenAI ChatCompletionMessageParam[]，含 system 提示词），使用 TypeScript OpenAI SDK 的 openai.beta.chat.completions.stream（MODEL = 'gpt-4o'）发起流式补全，并返回一个 SSE 流。它把 OpenAI 的增量事件重映射为三种前端可消费的事件，每个都编码为 data: <json>\n\n：

  • assistant_delta —— delta.content 的普通文本增量；
  • function_arguments_delta —— delta.tool_calls[0] 的增量参数，携带 callId、name、增量 arguments；
  • function_arguments_done —— 当 finishReason === 'tool_calls' 时发送，携带累积的完整 arguments，随后重置累积状态。

请求体里的 tools（来自 lib/tools.ts 的 search_location 与 plan_itinerary）作为 OpenAI 工具传给模型。响应头为 Content-Type: text/event-stream、Cache-Control: no-cache、Connection: keep-alive。任何异常返回 { error: message } 的 500 JSON。

/api/search_location —— SerpAPI 搜索

POST /api/search_location 接收 { location, search_query }，从 process.env.SERPAPI_API_KEY 读取密钥（缺失则抛错），用 serpapi 包的 getJson（engine: 'google'、limit: 5）检索，返回 response.organic_results 作为 JSON。前端 handleTool 在模型发起 search_location 工具调用时调用此路由，voice-mode 组件处理 Realtime 触发的 search_location 时也复用此路由。

/api/create_itinerary —— 行程规划

POST /api/create_itinerary 接收 { stops }，用 model o1 和 ITINERARY_PROMPT（system）调用 openai.chat.completions.create，把 stops JSON 作为 user 内容，返回 { itinerary: result }。前端 handleTool 把模型发起的 plan_itinerary 工具调用转发到此路由（端点名与工具名不同，是两者之间的映射点）。

/api/session —— Realtime API 前置步骤

GET /api/session 是语音模式专属的前置步骤，为 OpenAI Realtime API 获取 ephemeral session token。它向 https://api.openai.com/v1/realtime/sessions 发起 POST，请求体含 model: gpt-4o-realtime-preview（REALTIME_MODEL）与 voice: coral（VOICE），请求头用 process.env.OPENAI_API_KEY 鉴权，并把响应体（含 client_secret）原样回传给前端。Flask 后端没有对应端点。

前端 voice-mode.tsx 的 startSession 先 fetch('/api/session') 取回 client_secret.value，再按该 token 将 SDP offer POST 到 https://api.openai.com/v1/realtime?model=gpt-4o-realtime-preview，建立 WebRTC 连接与 oai-events data channel。

Flask 后端（python-backend/app.py）

Flask 后端是 Next.js 路由的等价替代而非子集。它用 Flask(__name__) 建应用、CORS(app) 开跨域、load_dotenv() 从 .env 加载环境变量、client = OpenAI() 初始化 SDK，并在 app.run(debug=True, port=8000) 运行于 8000 端口。四个端点：

  • GET / —— 返回 "Server is running"（健康检查，Next.js 无对应）。
  • POST /get_response —— 接收 { messages }，以 MODEL = "gpt-4o" 和同一份 tools 定义（search_location、plan_itinerary，内嵌于 app.py）调用 client.chat.completions.create，返回完整的 completion.choices[0].message JSON。注意：它不流式（与 Next.js 的 SSE 流不同），因此若前端 assistant.ts 仍按 SSE 解析会得到单块 JSON；切换后端需同步调整客户端解析方式。
  • POST /search_location —— 读取 os.getenv('SERPAPI_API_KEY')（缺失抛 ValueError），用 serpapi 的 GoogleSearch(params).get_dict() 检索，返回 results["organic_results"]。与 Next.js 版本等价（同为 engine: google、limit: 5），只是把 getJson 换成 GoogleSearch。
  • POST /plan_itinerary —— 接收 { stops }，与 Next.js /api/create_itinerary 完全等价：model o1 + ITINERARY_PROMPT（内嵌于 app.py）+ json.dumps(stops)，返回 { "itinerary": ... }。

同一定义（工具 schema、提示词、SDK 调用）在 Next.js 版本中分散在 lib/constants.ts、lib/tools.ts 与各 route，而在 Flask 版本中集中于 app.py。两处 ITINERARY_PROMPT 与两处 MODEL = "gpt-4o" 文本一致。

环境变量与配置

两个后端都需要 OPENAI_API_KEY（在 lib/assistant.ts new OpenAI()、Flask client = OpenAI() 中由 SDK 自动读取；/api/session 显式使用 process.env.OPENAI_API_KEY）。搜索功能需要 SERPAPI_API_KEY：Next.js 在 /api/search_location 中读 process.env.SERPAPI_API_KEY（缺失抛错），Flask 在 /search_location 中读 os.getenv('SERPAPI_API_KEY')（缺失抛 ValueError）。

Flask 后端用 python-dotenv（load_dotenv()）从 .env 加载密钥；仓库中的 .env.example 只列了 OPENAI_API_KEY=<your-openai-api-key>。Next.js 前端用 .env / .env.local 提供密钥（/.gitignore 忽略 .env 与 .env*.local）。依赖清单见 python-backend/requirements.txt（Flask、Flask-Cors、openai、serpapi 的 google_search_results、python-dotenv 等），前端依赖见 package.json（openai、serpapi、next 等）。

错误处理对照

Next.js 路由统一用 try/catch 包裹，失败返回 { error: <message> } + HTTP 500；/api/get_response 额外在流的 start 内部 catch，失败时 controller.error(error) 终止流；/api/search_location 与 Flask /search_location 都会在缺少 SERPAPI_API_KEY 时抛错。Flask 端点默认由 Flask/Werkzeug 返回 500 错误页（未像 Next.js 那样统一包裹为 JSON），错误处理比 Next.js 路由更原始。

前端常量（lib/constants.ts）

challenge5/frontend/lib/constants.ts 是前端参数的单一集中来源，各导出值被 assistant.ts、voice-mode.tsx、app/api/session/route.ts 等消费。逐项说明：

  • MODEL：值为 gpt-4o，用于非流式的对话补全（/api/get_response 后端默认模型也定义为 gpt-4o）。
  • REALTIME_MODEL：值为 gpt-4o-realtime-preview，用于 OpenAI Realtime API 的实时语音对话。
  • REALTIME_BASE_URL：值为 https://api.openai.com/v1/realtime，voice-mode.tsx 将模型参数拼接到该 URL 上发起 WebRTC 的 SDP 握手。
  • VOICE：值为 coral，在 /api/session 路由请求 ephemeral token 时传给 Realtime 会话。
  • SYSTEM_PROMPT：旅行助手“Wanderlust Concierge”的系统提示词，指导助手询问出行地点与时长、推荐目的地/活动/住宿，并在合适时机调用 search_location 工具。
  • INITIAL_MESSAGE：聊天窗口的初始消息（“Hi, how can I help you for your upcoming trip?”）。
  • ITINERARY_PROMPT：行程规划推理提示词，指导根据停留时长、访问类型与人数规划最优游览顺序。该提示词文本与 Python 后端 app.py 中的 ITINERARY_PROMPT 完全一致。
  • REALTIME_PROMPT：Realtime 语音会话专用的热情洋溢版旅行助手提示词。
  • REALTIME_TOOLS：Realtime 会话暴露给模型的工具定义，当前仅包含 search_location（按地点与查询词搜索地标或酒店）。

需要注意前端存在两套并列的工具定义：constants.ts 的 REALTIME_TOOLS 用于 Realtime 语音会话，而 lib/tools.ts 导出的 tools（含 search_location 与 plan_itinerary）用于普通文本对话的工具调用。SYSTEM_PROMPT / ITINERARY_PROMPT / REALTIME_PROMPT 分别对应普通对话、行程规划与语音会话三个场景。

next.config.mjs

challenge5/frontend/next.config.mjs 仅导出空对象：

/** @type {import('next').NextConfig} */
const nextConfig = {};
export default nextConfig;

这是一个空默认配置，没有任何特殊行为：未启用实验性特性、未配置 rewrite/redirect、未设置环境变量映射。项目依赖 Next.js 默认约定（如自动读取 .env / .env.local）。因此若需新增构建或代理行为，需在此处显式添加配置。

环境变量

整个系统将密钥与可变配置放入环境变量，而非硬编码在源码中。.env 文件被 .gitignore 忽略，源码仓库只提交 .env.example 模板。

前端环境变量

  • OPENAI_API_KEY：openai SDK（服务端 app/api/* 路由）会自动读取该变量。例如 /api/session/route.ts 用 process.env.OPENAI_API_KEY 作为 Bearer token 换取 Realtime ephemeral token。
  • SERPAPI_API_KEY：app/api/search_location/route.ts 读取，用于 Google Search。该路由在缺少该变量时抛出 SERPAPI_API_KEY is not defined 错误并返回 500。

前端项目本身没有提交 .env.example 文件；密钥约定与后端一致（见下）。

Python 后端环境变量

challenge5/python-backend/.env.example 是后端的环境变量模板，仅定义：

OPENAI_API_KEY=<your-openai-api-key>

后端启动时通过 python-dotenv 的 load_dotenv() 加载项目根目录下的 .env 文件（app.py 顶部 from dotenv import load_dotenv 后调用 load_dotenv()）。随后：

  • client = OpenAI() 依赖 openai SDK 自动从环境读取 OPENAI_API_KEY。
  • /search_location 路由用 os.getenv('SERPAPI_API_KEY') 读取密钥，若未定义则 raise ValueError('SERPAPI_API_KEY is not defined')。

因此后端至少需要 OPENAI_API_KEY 才能工作；若使用 search_location 功能则还需配置 SERPAPI_API_KEY（该变量未出现在 .env.example 模板中，需手动补充）。

配置与运行的关系

调整运行时行为时需注意配置的消费位置：

  • 更换模型可在 constants.ts 的 MODEL / REALTIME_MODEL 修改；常用文本对话同时受后端 app.py 的 MODEL 影响。
  • 更换语音在 constants.ts 的 VOICE 修改，经 /api/session 传入 Realtime。
  • 提示词语气在各 *_PROMPT / SYSTEM_PROMPT 中调整，普通对话与语音会话使用不同提示词。
  • 新增或调整工具：语音会话改 REALTIME_TOOLS，文本对话改 lib/tools.ts 的 tools，同时保持 handleTool 与对应 API 路由一致。

03 · frontend-components.md

前端组件与状态管理

前端 UI 位于 frontend/（每个 challenge 目录下各有一份 Next.js App Router 应用）。UI 层围绕一个旅行助手聊天界面组织：Assistant 持有整个会话状态，把 chatMessages 下发给 Chat；Chat 按条目类型（type）分发到 Message 或 ToolCall 渲染；Assistant 通过 useConversationStore（zustand）读写会话状态。challenge4 起，Chat 的输入工具栏新增了 VoiceMode 按钮，用于切换到 OpenAI Realtime 语音会话。

组件树与数据流

整体组件树和数据流向如下：

flowchart TD Page["app/page.tsx - Main"] Page --> Assistant["Assistant (components/assistant.tsx)"] Assistant --> Store["useConversationStore (zustand)"] Assistant --> Chat["Chat (components/chat.tsx)"] Chat --> Msg["Message (message.tsx)"] Chat --> TC["ToolCall (tool-call.tsx)"] Chat --> VM["VoiceMode (voice-mode.tsx) - challenge4+"] Store -->|"chatMessages: Item[]"| Assistant Assistant -->|"addChatMessage / addConversationItem"| Store Chat -->|"items + onSendMessage + loading"| Assistant Chat -->|"item.type 分发"| Msg Chat -->|"item.type 分发"| TC

组件树：page.tsx 渲染 Assistant；Assistant 持有 store 状态的读写入口并把 chatMessages 传给 Chat；Chat 根据 item.type 分发渲染 Message 或 ToolCall；challenge4/5 在 Chat 输入工具栏加入 VoiceMode 按钮。

组件职责：

  • app/page.tsx（Main）：应用根页面，居中布局并渲染唯一的 <Assistant />（见 starting_point/frontend/app/page.tsx、challenge5/frontend/app/page.tsx，两处均为 241 字节的同一结构）。
  • Assistant：'use client' 组件，是 UI 与 store、自研 lib/assistant 的桥。它从 store 取出 chatMessages 和 add 动作，定义 handleSendMessage（把用户输入构造成一个 Item 与一个 ChatCompletionMessageParam，分别 addChatMessage / addConversationItem，然后进入推理流程），并把 items、onSendMessage、loading 作为 props 传给 Chat。starting_point 版用本地 loading 状态控制加载，challenge5 版去掉了 loading 并改用 processMessages()。
  • Chat：接受 items: Item[] 与 onSendMessage（以及 starting_point/challenge4 的 loading）。维护输入框 textarea 的本地状态，Enter 发送；维护 itemsEndRef 并在 items 变化后滚动到底部。对每个 item，item.type === 'function_call' 时渲染 ToolCall（并传入 previousItem），否则渲染 Message。challenge4/5 在输入框与发送按钮之间插入 <VoiceMode />。
  • Message：接收 MessageItem。按 role 分左右布局（user 右对齐 white，assistant 左对齐 black），用 react-markdown 渲染 content。starting_point/challenge4 版支持 loading（渲染三点动画）；challenge5 版去掉了 loading 分支。
  • ToolCall：接收 FunctionCallItem 与 previousItem，用于展示工具调用卡片。标题由 functionCall.name 按 _ 拆分后转大驼峰显示，右侧有可点击箭头（ChevronRight）展开/收起详情。展开后通过 react-syntax-highlighter（Prism/coy 主题）以 JSON 显示 parsedArguments，并在有 output 时显示解析后的输出。若 previousItem.type === 'function_call'，渲染一段竖向连接线（视觉上把连续工具调用串起来）。challenge5 版将可复用的展示逻辑拆成内部的 ApiCallCell。
  • VoiceMode：challenge4/5 的实时语音组件，本身是一个麦克风图标按钮，使用 WebRTC 与 OpenAI Realtime API 建立会话（通过 /api/session 获取临时 token，创建 RTCPeerConnection 和 oai-events 数据通道），在输入工具栏中与文本发送按钮并排。实时路径不写入 useConversationStore，而是独立管理自己的 RTCDataChannel / peer connection 状态。

Item 联合类型与 ToolCall 展示

lib/assistant.ts 定义了两个可辨识联合类型（discriminated union）：

  • MessageItem：{ type: 'message'; role: 'user' | 'assistant' | 'system'; content: string }
  • FunctionCallItem：{ type: 'function_call'; status: 'in_progress' | 'completed' | 'failed'; id; name; arguments; parsedArguments: any; output: string | null }
  • Item = MessageItem | FunctionCallItem

Chat 通过 item.type 区分两者并分发到不同组件：function_call 走 ToolCall，否则走 Message。ToolCall 据此读取 FunctionCallItem 上的字段：name 显示为标题，parsedArguments 以 JSON 呈现可展开的参数，output（存在时）以 JSON 呈现工具返回结果。status 字段在这一版本的 ToolCall 中尚未用于视觉状态（标题固定显示），但为流式更新记录了工具调用的生命周期。参见 starting_point/frontend/lib/assistant.ts#L5-L21 与 challenge5/frontend/lib/assistant.ts#L7-L23、challenge5/frontend/components/tool-call.tsx。

zustand 状态管理：useConversationStore

stores/useConversationStore.ts 用 zustand 的 create 定义会话状态，管理两类互相独立的数组：

  • chatMessages: Item[]：用户可见的聊天条目（MessageItem | FunctionCallItem），驱动 Chat/Message/ToolCall 渲染。初始值是一条 assistant 的 INITIAL_MESSAGE。
  • conversationItems: ChatCompletionMessageParam[]：发给 Chat Completions API 的消息结构（含 role、content、以及工具调用/工具输出），初始为空。

Store 暴露 setChatMessages / setConversationItems（整体替换）与 addChatMessage / addConversationItem（追加单条）。Assistant（及其调用的 processMessages/handleTurn）维护这两个数组的并行一致性：用户输入同时追加到两者；流式回复时两者同步累积。推理逻辑（在 lib/assistant.ts）通过 useConversationStore.getState() 读取当前快照并对两个数组做同步更新。参见 starting_point/frontend/stores/useConversationStore.ts 与 challenge5/frontend/stores/useConversationStore.ts（两处实现一致）。

streaming 下的 Message 与 ToolCall 实时更新

在 challenge5 中，推理不再一次性返回，而是由 /api/get_response（app/api/get_response/route.ts）以 text/event-stream 流式推送事件，前端 handleTurn 用 fetch 的 ReadableStream 读取 SSE 数据，逐条调用 onMessage 回调。processMessages 在 lib/assistant.ts 中按事件类型增量更新两个数组：

  • assistant_delta：追加/更新 assistantMessageContent。若 chatMessages 末尾是 assistant 的 message，就地 content = assistantMessageContent（实现打字机效果）；否则 push 一条新的 assistant message。conversationItems 做相同处理（末尾 assistant 消息就地更新，否则 push）。每次更新后调用 setChatMessages([...]) / setConversationItems([...])（新数组引用触发 zustand 订阅与 React 重渲染）。
  • function_arguments_delta：累积 functionArguments，用 partial-json 的 parse 生成 parsedArguments。若 chatMessages 末尾是同一 callId 的 function_call，就地更新 arguments / parsedArguments；否则 push 一条 status: 'in_progress' 的新 function_call。conversationItems 同步累积 tool_calls[0].function.arguments。
  • function_arguments_done：工具参数收集完毕，调用 handleTool(name, parse(functionArguments)) 执行工具（如 search_location、plan_itinerary，见 lib/tools.ts），把结果设为 chatMessages 末尾 function_call 的 status: 'completed' 与 output，并向 conversationItems push 一条 role: 'tool' 的消息，然后递归调用 processMessages() 让模型基于工具结果继续输出。

因此，Message 的文本与 ToolCall 的参数/输出都是随流式事件逐步原地更新的，而非整体重建。参见 challenge5/frontend/lib/assistant.ts#L85-L241 与 challenge5/frontend/app/api/get_response/route.ts。

扩展点：ui 套件

challenge5/frontend/components/ui/ 下提供 button.tsx、chart.tsx、table.tsx 三个 shadcn/ui 风格的原子组件。其中 chart.tsx（基于 recharts 的 ChartContainer/ChartTooltip/ChartLegend）与 table.tsx（Table/TableHeader/TableBody 等）在 demo 的业务组件（assistant/chat/message/tool-call/voice-mode）中均未被引用，仅各自自引，编译产物不包含它们——它们是为未来 UI 预留的扩展点，可用于把 itinerary/搜索结果以图表或表格形式展示。button.tsx 同样未被业务代码 import。

开始变更前注意：ui 组件使用 @/lib/utils 中的 cn，装饰器/主题（如 cva、THEMES.dark）依赖 globals.css 与 tailwind.config.ts 中的 CSS 变量，接入时需要确保这些变量已定义。

starting_point：默认固定回复

starting_point 是一个前后端骨架，不含任何真实 AI 能力。

  • 前端 frontend/app/api/get_response/route.ts 只 await new Promise(resolve => setTimeout(resolve, 2000)) 睡眠 2 秒，然后返回硬编码的 JSON { role: 'assistant', content: 'This is a default message, update the backend to get a response from the OpenAI API instead.' }。
  • 对应 python-backend app.py 的 /get_response 同样 time.sleep(2) 后返回相同的固定文案。
  • 前端 lib/tools.ts 是空壳：export const tools = []，handleTool 为空函数；lib/assistant.ts 的 handleTurn 只做一次非流式 fetch('/api/get_response')。

关键文件：frontend/app/api/get_response/route.ts（Next.js 版）、python-backend/app.py 的 /get_response（Python 版）。两处的 get_response 是教程里先后端实现的前端点。

challenge1：对接 OpenAI Chat Completions

第一个关卡把占位回复换成真实模型对话。

  • 前端 frontend/app/api/get_response/route.ts 用 openai.chat.completions.create({ model: MODEL, messages }) 调用 OpenAI，MODEL 来自 lib/constants.ts（gpt-4o），返回 response.choices[0].message。system prompt 已包含在 messages 数组里。
  • python-backend app.py 用 client.chat.completions.create(model=MODEL, messages=messages) 做同样的事，completion.choices[0].message 作为 JSON 返回。

新增能力：真实对话。前端关键改动是 get_response 路由；后端对应改动是 app.py 的 /get_response。此时还没有任何工具。

challenge2：新增 search_location 工具与工具调用循环

第二个关卡引入函数调用（tool calling）：模型可以请求调用搜索工具，前端执行并回填结果。

  • 前端 lib/tools.ts 定义了 tools 数组，包含 search_location 工具（JSON Schema 描述 location 与 search_query 两个必填参数）；handleTool(toolName, parameters) 在该工具被调用时 fetch('/api/search_location') 并返回结果。
  • 前端 app/api/get_response/route.ts 把 tools 一并传给 openai.chat.completions.create。
  • 前端 lib/assistant.ts 的 handleTurn 增加工具调用循环：拿到 assistant 消息后，若含 tool_calls，则用 handleTool 执行并把结果以 role: 'tool' 的消息推回对话，然后递归再调 handleTurn() 让模型基于工具结果继续作答。
  • 前端 app/api/search_location/route.ts 用 serpapi 包 getJson({ engine: 'google', ... }) 搜索，SERPAPI_API_KEY 来自 process.env。
  • python-backend app.py 定义同名的 tools 列表，/get_response 把 tools=tools 传给 API；/search_location 用 GoogleSearch(params)（同样 SerpAPI Google 引擎）返回 organic_results。

新增能力：外部数据 + 多轮工具循环。前端关键改动是 lib/tools.ts（tools 数组 + handleTool）、lib/assistant.ts（递归工具循环）、app/api/search_location/route.ts；后端对应 app.py 的 tools 与 /search_location。

challenge3：新增 plan_itinerary 推理规划工具

第三个关卡加入第二个工具，用 o1 推理模型做行程规划。

  • 前端 lib/tools.ts 的 tools 数组追加 plan_itinerary（参数为 stops 数组，含 location、duration、type、participants），handleTool 增加分支：该工具被调用时 fetch('/api/create_itinerary')。
  • 前端 app/api/create_itinerary/route.ts 用 model o1 + ITINERARY_PROMPT（system）调用 openai.chat.completions.create，把 stops JSON 作为 user 内容，返回 { itinerary: ... }。
  • lib/constants.ts 新增 ITINERARY_PROMPT，并把 system prompt 升级为 "Wanderlust Concierge" 引导式旅行助手。
  • python-backend app.py 同步新增 plan_itinerary 工具定义与 /plan_itinerary 端点（也使用 model="o1" + ITINERARY_PROMPT）。

新增能力：推理型规划。前端关键改动是 lib/tools.ts、app/api/create_itinerary/route.ts、lib/constants.ts；后端对应 app.py 的 plan_itinerary 与 /plan_itinerary。工具循环仍由 assistant.ts 驱动，无需改动。

challenge4：新增实时语音模式

第四个关卡加入实时语音对话，走 OpenAI Realtime API + WebRTC，与文本聊天并行。

  • 前端新增 components/voice-mode.tsx：startSession() 先 fetch('/api/session') 拿 ephemeral token，再 new RTCPeerConnection() 建连接、getUserMedia 取麦克风、createDataChannel('oai-events')，按 token 将 SDP offer POST 到 REALTIME_BASE_URL?model=REALTIME_MODEL。
  • 前端 app/api/session/route.ts 是语音专属前置步骤：向 https://api.openai.com/v1/realtime/sessions POST，请求体 { model: REALTIME_MODEL, voice: VOICE }，用 process.env.OPENAI_API_KEY 鉴权，把含 client_secret 的响应原样回传，浏览器侧用 client_secret.value 鉴权。
  • lib/constants.ts 新增 REALTIME_MODEL（gpt-4o-realtime-preview）、REALTIME_BASE_URL、VOICE（coral）、REALTIME_PROMPT。
  • 此时 data channel 的 conversation.item.created 处理器是空的（const output = event 但未使用），session.update 只发送 instructions，还不处理工具调用。
  • python-backend 没有对应变更：语音模式完全在前端直连 Realtime API 完成，Flask 后端只是文本/工具路径的替代实现。

新增能力：实时语音。前端关键改动是 components/voice-mode.tsx、app/api/session/route.ts、lib/constants.ts；后端无对应路由。

challenge5：SSE 流式传输 + 语音内工具调用

第五个关卡是最终形态，同时演进文本与语音两条链路。

  • 文本改流式：app/api/get_response/route.ts 改用 openai.beta.chat.completions.stream 并返回 ReadableStream，响应头 Content-Type: text/event-stream。它把 OpenAI 的增量重映射为三类 SSE 事件：assistant_delta（文本增量）、function_arguments_delta（工具参数增量）、function_arguments_done（finishReason === 'tool_calls' 时携带完整参数）。
  • lib/assistant.ts 重构为 handleTurn(messages, onMessage) + processMessages()：用 response.body.getReader() 逐块读取 SSE，TextDecoder 按 data: json 行解析（支持 [DONE]），partial-json 的 parse 解析增量参数；完成工具调用后用 role: 'tool' 消息回填并递归 processMessages()。
  • 语音加工具：components/voice-mode.tsx 的 session.update 现在发送 tools: REALTIME_TOOLS（来自 lib/constants.ts，定义 search_location 简化版），data channel 收到 conversation.item.created 且 type === 'function_call' 时调用 handleToolCall：把 search_location 转发到 /api/search_location，再用 conversation.item.create 发回 function_call_output，并强制 response.create 让模型基于结果继续回答。
  • python-backend 仍无对应变更（与 challenge4 一致），因语音按 Realtime API 直接工作、文本流式由 Next.js 路由处理。

新增能力：流式文本 + 语音内工具调用。前端关键改动是 app/api/get_response/route.ts、lib/assistant.ts、components/voice-mode.tsx、lib/constants.ts（REALTIME_TOOLS）。

前端 tools.ts 与后端 route 的配合机制

lib/tools.ts 是整个工具链的契约中心，把"模型能调什么"和"前端执行什么"绑在一起：

  • tools 数组定义的函数 Schema 原样传给 OpenAI API（在 get_response 路由里作为 tools 参数传入 chat.completions.create，或流式版本的 openai.beta.chat.completions.stream 的 tools）。模型据此决定何时、以何参数发起工具调用。
  • handleTool(toolName, parameters) 根据工具名分派到对应 API 路由：search_location → fetch('/api/search_location')，plan_itinerary → fetch('/api/create_itinerary')。工具名与前端的路由名是两个独立命名空间，plan_itinerary → /api/create_itinerary 就是这种映射点。

外部集成（OpenAI / SerpAPI / Realtime）

本页汇总 Wanderlust Concierge 依赖的全部外部服务接口及其接入方式。前端（Next.js API 路由）与 Python（Flask）两套后端都会代理这些外部请求，把密钥留在服务端，避免暴露给浏览器。三个外部依赖分别是：

  1. OpenAI Chat Completions —— 文本对话补全 + 工具调用；
  2. OpenAI Realtime API —— 基于 WebRTC 的实时语音会话；
  3. SerpAPI Google 搜索 —— 地标 / 酒店的互联网搜索。

这些服务都以 API 密钥鉴权，密钥从 .env 环境变量读取。下文分别说明每个服务的鉴权方式、请求示例、响应格式与典型错误场景，最后汇总 .env 配置方式。

OpenAI Chat Completions

文本对话与行程规划都调用 OpenAI Chat Completions，但走两条不同的补全路径。

SDK 鉴权

前端与后端都通过 SDK 默认构造器读取 OPENAI_API_KEY，无需在代码里显式传密钥：

  • 前端 app/api/get_response/route.ts 与 app/api/create_itinerary/route.ts：new OpenAI()，由 openai npm 包默认读取 process.env.OPENAI_API_KEY。
  • Python 后端 app.py：client = OpenAI()，由 openai Python SDK 默认读取环境里的 OPENAI_API_KEY（由顶部 load_dotenv() 从 .env 载入）。

唯一显式使用该密钥的位置是 /api/session 路由——它在服务端拼出 Authorization: Bearer ${process.env.OPENAI_API_KEY} 头去换取 Realtime ephemeral token（见下文）。

流式对话：/api/get_response

前端 app/api/get_response/route.ts 使用 openai.beta.chat.completions.stream({ model: 'gpt-4o', messages, tools }) 做流式补全，并把 OpenAI 增量 delta 重映射为三种 SSE 事件（assistant_delta / function_arguments_delta / function_arguments_done）下发给前端。底层 openai 包接受 tools 数组，使模型可以发起 search_location 与 plan_itinerary 工具调用，返回 choices[0].message（流式场景下为带 delta.tool_calls 的增量）。该路由用 ReadableStream 逐块 controller.enqueue，响应头为 Content-Type: text/event-stream、Cache-Control: no-cache、Connection: keep-alive。

对应的 Flask 端点 POST /get_response 是非流式等价实现：client.chat.completions.create({ model: 'gpt-4o', messages, tools })，一次返回完整的 completion.choices[0].message JSON（其中可含 tool_calls）。两套实现对工具 schema、模型名保持一致。

非流式行程规划：/api/create_itinerary 与 /plan_itinerary

app/api/create_itinerary/route.ts 与 Flask POST /plan_itinerary 使用 model o1 做非流式补全：openai.chat.completions.create({ model: 'o1', messages: [system(ITINERARY_PROMPT), user(json.dumps(stops))] })，返回 { itinerary: content }。此处刻意选用推理模型 o1 而非对话模型的 gpt-4o，因为行程优化需要推理能力。

典型错误场景

  • 缺少 OPENAI_API_KEY：openai SDK 构造或首次请求时抛出认证错误；各 route 用 try/catch 捕获并返回 { error: <message> } + HTTP 500。
  • 网络错误 / 上游故障：/api/get_response 在流的 start 内部 catch，失败时 controller.error(error) 终止 SSE 流；外层 catch 返回 500 JSON。
  • 无效或过期密钥：上游返回 401，SDK 抛错，被同一 catch 捕获为 500。

OpenAI Realtime API（WebRTC 语音）

Realtime 集成是前置 /api/session 换取 ephemeral token，再在浏览器用该 token 通过 WebRTC 做 SDP 交换，并在 oai-events data channel 上收发事件。

换取短期 token：/api/session

GET /api/session（app/api/session/route.ts）在服务端向 https://api.openai.com/v1/realtime/sessions 发起 POST，请求头用 Authorization: Bearer ${process.env.OPENAI_API_KEY}，请求体为 { model: 'gpt-4o-realtime-preview'（REALTIME_MODEL）, voice: 'coral'（VOICE） }，并把响应体原样回传。该响应含 client_secret（短期有效 token），避免把长期密钥交给前端。

WebRTC 握手与音频：voice-mode.tsx

前端 components/voice-mode.tsx 的 startSession 流程：

  1. fetch('/api/session') 取回 client_secret.value 与会话 id。
  2. 新建 RTCPeerConnection，把 navigator.mediaDevices.getUserMedia({ audio: true }) 采集的音频轨道 addTrack 进连接，并用 pc.ontrack 把远端音频接到 <audio> 元素播放。
  3. createOffer() → setLocalDescription(offer)，把 offer.sdp POST 到 https://api.openai.com/v1/realtime?model=gpt-4o-realtime-preview（REALTIME_BASE_URL 拼模型参数），请求头 Authorization: Bearer ${client_secret.value}、Content-Type: application/sdp；把返回的 SDP 作为 answer setRemoteDescription。

连接建立后：

  • pc.createDataChannel('oai-events') 传输事件；data channel open 时发送 session.update（instructions 用 REALTIME_PROMPT，tools 用 REALTIME_TOOLS），并把 isSessionActive 置真。
  • 收到模型发来的 conversation.item.created 且类型为 function_call 时，前端调用 handleToolCall：对 search_location 转发到 /api/search_location，再把输出作为 conversation.item.create（type: 'function_call_output'）经 data channel 回传，随后 response.create 促使模型继续。
  • 挂断时 stopSession 关闭 data channel 与 peer connection，并停止本地音频轨道。

典型错误场景

  • /api/session 失败（缺密钥 / 网络）：返回 { error } + 500，语音模式拿不到 client_secret 无法继续。
  • SDP 交换失败 / token 过期：setRemoteDescription 或 fetch 抛错，被 startSession 的 catch 记录，会话无法激活。
  • data channel 未打开就发送事件：sendClientEvent 打印 "Failed to send message - no data channel available" 并丢弃。

SerpAPI Google 搜索

SerpAPI 负责 search_location 工具的互联网检索（地标、酒店等）。

鉴权与请求

前端 app/api/search_location/route.ts 用 serpapi 包的 getJson：

getJson({
  engine: 'google',
  q: search_query,
  location: location,
  api_key: SERPAPI_API_KEY,   // 来自 process.env
  limit: 5
})

返回对象取 response.organic_results 作为 JSON 响应。Python 后端 app.py 的 /search_location 使用同包等价的 GoogleSearch(params).get_dict()，params 字段完全一致（engine/q/location/api_key/limit），同样取 results["organic_results"]。两端都固定 engine: 'google' 与 limit: 5。

前端 lib/tools.ts 的 handleTool 在模型发起 search_location 工具调用时转发到此路由；语音模式 voice-mode.tsx 收到 Realtime function_call 时也复用同一路由。

典型错误场景

  • 缺少 SERPAPI_API_KEY：前端路由显式 if (!serpApiKey) throw new Error('SERPAPI_API_KEY is not defined')，被路由 catch 捕获返回 { error } + 500；Flask 端点等价地 raise ValueError('SERPAPI_API_KEY is not defined')（Flask 默认返回 500 错误页而非 JSON）。
  • 网络 / 上游限流错误：getJson / get_dict() 抛错，同样被 catch 变为 500。

.env 密钥配置

密钥统一由环境变量提供，process.env 与 Flask 的 load_dotenv() 从 .env 读取；.env 文件本身被 .gitignore 忽略，仓库只提交 .env.example 模板。

变量 用途 消费位置
OPENAI_API_KEY Chat Completions 与 Realtime 鉴权 openai SDK 自动读取（/api/get_response、/api/create_itinerary、Flask client）；/api/session 显式 process.env / Bearer 头
SERPAPI_API_KEY SerpAPI Google 搜索 /api/search_location 读 process.env；Flask /search_location 读 os.getenv

配置方式：

  • 前端（Next.js）：next.config.mjs 当前为空默认配置，项目依赖 Next.js 默认约定自动读取 .env / .env.local；服务端 route 通过 process.env.* 访问。路由以这种方式承接 OPENAI_API_KEY 与 SERPAPI_API_KEY。
  • Python 后端：app.py 顶部 from dotenv import load_dotenv; load_dotenv() 从项目根目录 .env 自动加载；随后 OpenAI() 自动读取 OPENAI_API_KEY，/search_location 用 os.getenv('SERPAPI_API_KEY') 读取。
  • 模板：starting_point/python-backend/.env.example 与 challenge5/python-backend/.env.example 均只列出 OPENAI_API_KEY=<your-openai-api-key>。SERPAPI_API_KEY 未出现在模板中，使用搜索功能前需手动补充该变量。

前端实现：Next.js 14 + React 18 + TypeScript

所有挑战的 frontend/ 都是同一个 Next.js 14（App Router）+ React 18 + TypeScript 应用模板（package.json 的 name 均为 convex，版本均锁定 next@14.2.11、react@^18）。前端组织方式固定为四层：

  • app/ —— 页面与 API 路由。page.tsx 渲染唯一的 <Assistant />；app/api/ 下存放后端路由（如 get_response、search_location、create_itinerary、session）。
  • components/ —— UI 组件（Assistant、Chat、Message、ToolCall，challenge4+ 增加 VoiceMode，challenge5 另有 ui/ 原子套件）。
  • lib/ —— 业务逻辑：constants.ts（系统 prompt、初始消息、模型名）、tools.ts（工具 Schema 与 handleTool 分派）、assistant.ts（对话/流式处理）、utils.ts。
  • stores/ —— useConversationStore，基于 zustand 的会话状态管理。

状态管理用 zustand：useConversationStore 维护两个平行数组——chatMessages（驱动 UI 的条目）与 conversationItems（发给 Chat Completions API 的消息结构），并提供 set/add 系列原子动作。样式用 Tailwind CSS：tailwind.config.ts 声明了基于 CSS 变量的 shadcn 风格主题（background、foreground、chart 等色板），globals.css 提供对应变量。复杂推理/流式流程由 lib/assistant.ts 通过 useConversationStore.getState() 读取快照并把两个数组同步更新。

聊天对话执行流程

本文档梳理文本聊天从用户输入到助手回复的单次完整回合的数据流。整个链路跨越四个层：React 组件（Assistant）、zustand 状态存储（useConversationStore）、业务逻辑（lib/assistant.ts）与后端路由（app/api/get_response/route.ts）。仓库中 challenge1-3 与 challenge5 对"一回合约"的建模方式截然不同：前者是一次请求-响应式、非流式，后者是 SSE 流式、逐事件增量处理。本文以 challenge5 的最终形态为主线，并与 challenge1-3 的非流式版本对比。

一条回合的执行主干

challenge5 下，单次文本回合的完整时序如下：

图：challenge5 一条文本回合的完整时序——用户输入入库后，processMessages 组装消息数组发给后端，后端以 SSE 流回推事件，前端逐事件原地更新 store 与 UI。

入口：Assistant.handleSendMessage

入口是 components/assistant.tsx 中 Assistant 组件的 handleSendMessage。它接收尚未清洗的原始 message 字符串，做四件事：

  1. 空消息守卫：if (!message.trim()) return —— 只含空白或空字符串的输入被直接跳过，不写入 store，也不触发后端请求（见 challenge5/frontend/components/assistant.tsx#L12-L13）。
  2. 构造双份消息结构：把 message.trim() 同时构造成一个 Item（{ type: 'message', role: 'user', content }，用于 UI 渲染）和一个 ChatCompletionMessageParam（{ role: 'user', content }，用于发给 Chat Completions API）。二者是同一用户输入的两种表示，分别写入 store 的 chatMessages 与 conversationItems。
  3. 写入 store：先 addConversationItem(userMessage) 再加入 addChatMessage(userItem)，保证两个平行数组并行更新。
  4. 触发推理：await processMessages() 启动流式回合（包裹在 try/catch 中，失败 console.error）。

与 challenge1-3 的差异在于：早期版本 Assistant 用一个本地 loading 状态控制 Chat 的加载动画，finally 中 setLoading(false)；challenge5 删掉了 loading，改为调用 processMessages()，靠流式事件驱动的重渲染完成 UI 更新。此外 challenge1 的 handleTurn 无需传参（内部从 store 取快照），而 challenge5 的 handleTurn(messages, onMessage) 由 processMessages 显式传入消息数组与事件回调。

状态存储的双数组模型

stores/useConversationStore.ts（starting_point 与 challenge5 实现一致）用 zustand create 维护两个互相独立的数组：

  • chatMessages: Item[] —— 用户可见的聊天条目（MessageItem | FunctionCallItem），驱动 Chat/Message/ToolCall 渲染，初始为一条 assistant 的 INITIAL_MESSAGE。
  • conversationItems: ChatCompletionMessageParam[] —— 发给 Chat Completions API 的消息结构（含 role、content、tool_calls、工具输出），初始为空。

Store 暴露整体替换（setChatMessages/setConversationItems）与单条追加（addChatMessage/addConversationItem）两类动作。推理逻辑通过 useConversationStore.getState() 读取当前快照（而非 React 闭包里的过期值），并在整个回合里对两个数组做同步更新。这条并行一致性约定贯穿整个回合：用户输入同时追加到两者，流式回复时两者同步累积，工具结果也同时反映到两者。

handleTurn：构造消息数组并发起 SSE 请求

lib/assistant.ts 的 handleTurn(messages, onMessage) 负责网络层：

  • 消息数组的拼接：processMessages 先把 SYSTEM_PROMPT（来自 lib/constants.ts 的旅行助手系统提示词）作为第一条 { role: 'system' } 消息，展开 conversationItems 追加其后，构成 [system, ...conversationItems] 的完整消息数组，再传给 handleTurn，最终作为 { messages } 的请求体 POST 给 /api/get_response。
  • 发起请求：fetch('/api/get_response', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ messages }) })。旁边保留注释的 http://localhost:8000/get_response 备选，用于切换 Flask 后端。
  • 非流式前身（challenge1-3）：早期 handleTurn 直接 fetch 后 await response.json() 拿到完整的一条 assistant MessageItem，一次性 push 进 chatMessages 与 conversationItems，无逐块读取。challenge5 改为 response.body!.getReader() 读取 ReadableStream，配合 TextDecoder 逐块解码、按 \n\n 切分 SSE 帧，提取 data: 前缀后的 JSON 再回调 onMessage(data)。

后端路由 app/api/get_response/route.ts 收到 { messages } 后，用 openai.beta.chat.completions.stream({ model: 'gpt-4o', messages, tools }) 发起流式补全，把 OpenAI 的增量事件重映射为三种前端可消费的 SSE 事件，每条编码为 data: <json>\n\n，并通过 ReadableStream 返回（响应头 Content-Type: text/event-stream、Cache-Control: no-cache、Connection: keep-alive）：

  • assistant_delta —— delta.content 的普通文本增量；
  • function_arguments_delta —— delta.tool_calls[0] 的增量参数，携带 callId、name、当块 arguments；
  • function_arguments_done —— 当 finishReason === 'tool_calls' 且正处于收集状态时发送，携带累积完整的 arguments，随后路由重置内部累积状态。

流结束时直接 controller.close()；[DONE] 是前端解析的终止信号（路由本身并不发送 [DONE]，是 OpenAI SDK 流迭代完即自然关闭）。请求体里的 tools（来自 lib/tools.ts 的 search_location 与 plan_itinerary 两个函数 Schema）作为 OpenAI 工具传给模型，模型据此决定何时发起工具调用。

processMessages：按事件类型增量更新

processMessages() 是 challenge5 重构出来的回合编排器。它先从 store 取当前快照，组装含 SYSTEM_PROMPT 的完整消息数组，调用 handleTurn，并在 onMessage 回调里按 event 类型分派增量更新。三个事件分支各自维护一组局部累积变量（assistantMessageContent、functionArguments）：

assistant_delta（文本打字机）

  • 累加 assistantMessageContent += data.content。
  • 若 chatMessages 末尾是 assistant 的 message，则就地 content = assistantMessageContent（产生逐字追加的打字机效果）；否则 push 一条新的 assistant message。之后调用 setChatMessages([...chatMessages])（新数组引用触发 zustand 订阅与 React 重渲染），再对 conversationItems 做相同处理（末尾 assistant 消息就地更新，否则 push）。

function_arguments_delta（工具参数实时累积）

  • 累加 functionArguments += data.arguments，并用 partial-json 的 parse 生成 parsedFunctionArguments（允许参数 JSON 尚未完整时容错解析）。
  • 若 chatMessages 末尾是同一 callId 的 function_call，则就地更新其 arguments/parsedArguments；否则 push 一条 status: 'in_progress' 的新 function_call。
  • 对 conversationItems 同步累积 tool_calls[0].function.arguments（末尾 assistant 消息已有 tool_calls 则就地改其参数，否则 push 一条带 tool_calls 的 assistant 消息）。

function_arguments_done（工具执行与递归续回合）

  • 参数收集完毕，调用 handleTool(data.name, parse(functionArguments)) 执行工具（search_location → /api/search_location、plan_itinerary → /api/create_itinerary，见 lib/tools.ts）。
  • 把 chatMessages 末尾对应 function_call 置为 status: 'completed' 并写入 output（序列化工具结果）；向 conversationItems push 一条 { role: 'tool', tool_call_id: data.callId, content: JSON.stringify(result) }。
  • 然后递归调用 processMessages() 再开一个回合，让模型基于工具结果继续作答，直到模型不再请求工具、返回纯文本 assistant_delta 为止。

边界行为与错误处理

边界行为

  • 空消息跳过：handleSendMessage 对 !message.trim() 直接 return，不写 store、不发请求（见上）。
  • [DONE] 终止：handleTurn 读取 SSE 行时若遇 data: [DONE] 置 done = true 并退出循环。
  • 流式中断的 buffer 余量：handleTurn 用 buffer 承接解码后尚未完整成帧的字节，按 \n\n 切分、把末段（可能是不完整帧）pop 回 buffer 留待下块拼接。循环结束后，若 buffer 中仍残留一条完整的 data: 帧（例如流在帧边界处结束），则在"处理 buffer 余量"的分支里再解析一次，避免丢尾。

错误处理（三层）

  • 前端 handleSendMessage：对 processMessages() 的 await 包裹 try/catch，失败 console.error('Error processing message:', error)。
  • 前端 handleTurn：response.ok 为 false 时 console.error('Error: ' + response.statusText)；整个读取过程再包一层 try/catch，异常 console.error('Error handling turn:', error)。
  • 后端路由 get_response：外层 POST handler 包 try/catch，失败返回 { error: message } + HTTP 500；流的 start 内部也包 try/catch，异常时 controller.error(error) 终止流。

编排上的自愈点：processMessages 通过递归续回合让流式工具调用天然变成多轮循环——单次 handleSendMessage 触发的一次 processMessages 可能内部递归多轮，直到模型产出最终文本。这取代了 challenge2-3 在 handleTurn 里检查 assistant 消息含 tool_calls 后手动递归的执行方式。

实时语音模式（Realtime API + WebRTC）

VoiceMode（components/voice-mode.tsx）是 Wanderlust Concierge 的实时语音对话入口，与文本聊天并行运行。它不经过 Flask 后端，也不复用文本的 get_response 路径，而是让浏览器直接通过 WebRTC 连上 OpenAI Realtime API：前半段由服务端 /api/session 换出 ephemeral token（鉴权凭据不落浏览器），后半段由浏览器自己完成 RTCPeerConnection 握手、SDP offer/answer 交换，以及经 oai-events 数据通道收发结构化 JSON 事件。challenge4 首度引入该链路（纯语音问答），challenge5 在其上叠加了语音内工具调用（search_location），使模型在语音会话里也能触发真实搜索。

组件挂在 components/chat.tsx 的发送按钮旁（<VoiceMode />），渲染为一个黑底圆钮，点击在"连接/断开"之间切换（见 challenge4/frontend/components/chat.tsx#L70 与 challenge5/frontend/components/chat.tsx#L70）。

配置常量（lib/constants.ts）

Realtime 语音的端点、模型、音色与提示词集中在 lib/constants.ts：

  • REALTIME_BASE_URL = 'https://api.openai.com/v1/realtime' —— SDP offer 的 POST 目标。
  • REALTIME_MODEL = 'gpt-4o-realtime-preview' —— Realtime 会话所用模型（与文本用的 gpt-4o/MODEL 不同）。
  • VOICE = 'coral' —— /api/session 请求体里选的音色。
  • REALTIME_PROMPT —— 语音助手的系统提示词，把语言模型塑造成"充满活力的 Wanderlust Concierge"旅行助手（与 SYSTEM_PROMPT 是不同文案）。
  • REALTIME_TOOLS（仅 challenge5）—— 语音会话注册的工具 Schema，只含一个简化的 search_location（location、search_query 两个字符串参数），描述"在特定地点搜索地标或酒店"。

入口与生命周期状态

组件维护两个 booleans：isSessionStarted（是否已发出过建连流程）与 isSessionActive（数据通道是否已 open），外加一个 dataChannel state 与几个 ref（peerConnection、audioElement、audioStream、audioTransceiver、tracks）。圆钮的 onClick 走 handleConnectClick：isSessionActive 为真则 stopSession()，否则 startSession()（见 challenge5/frontend/components/voice-mode.tsx#L202-L210）。isSessionActive 生效时按钮加上 animate-pulse 脉动动画提示正在通话。

startSession：建立语音会话

startSession() 是建连主干，challenge4 与 challenge5 实现完全一致（challenge5/frontend/components/voice-mode.tsx#L28-L97）：

  1. 取 ephemeral token：fetch('/api/session').then(r => r.json())，从响应里解出 session.client_secret.value 与 session.id。client_secret.value 是浏览器后续鉴权 SDP 请求所持的短时凭据。
  2. 建 peer connection：new RTCPeerConnection()。
  3. 准备远端音频播放：懒创建 audioElement（document.createElement('audio')），设 autoplay = true；pc.ontrack 回调把 e.streams[0] 赋给 audioElement.srcObject，模型合成的回答语音由此播出。
  4. 采麦克风：navigator.mediaDevices.getUserMedia({ audio: true })，把 stream.getTracks() 逐个 pc.addTrack(track, stream)，并把返回的 RTCRtpSender 记进 tracks.current。
  5. 建数据通道：pc.createDataChannel('oai-events')（固定名），setDataChannel(dc) 存入 state。该通道是后续收发 Realtime 事件的载体。
  6. SDP 握手：pc.createOffer() → setLocalDescription(offer) → 把 offer.sdp 文本用 POST 发到 `${REALTIME_BASE_URL}?model=${REALTIME_MODEL}`，请求头 Authorization: Bearer <sessionToken>、Content-Type: application/sdp；响应体是该模型对 offer 的 SDP answer（纯文本），包成 { type: 'answer', sdp } 后 setRemoteDescription(answer) 完成握手。
  7. 成功后 peerConnection.current = pc。

整个 startSession 由 if (!isSessionStarted) 守卫，保证同一次挂载只建一条连接；异常统一 console.error('Error starting session:', error)。

session.update 与事件监听（数据通道 open 后）

useEffect 在 dataChannel 创建后挂监听器（challenge4 见 challenge4/frontend/components/voice-mode.tsx#L130-L155，challenge5 见 challenge5/frontend/components/voice-mode.tsx#L136-L200）。open 事件触发时：

  • setIsSessionActive(true)（UI 进入活跃态、按钮脉冲）。
  • 发送 session.update 注入会话配置：challenge4 只发 { instructions: REALTIME_PROMPT }；challenge5 额外带上 { tools: REALTIME_TOOLS }，把 search_location 注册给模型，是语音内工具调用的前提。

sendClientEvent 是统一的出站函数：若 dataChannel 存在，给事件补 event_id（缺省用 crypto.randomUUID()）后 JSON.stringify 发上通道；否则 console.error('Failed to send message - no data channel available', ...)。

challenge4 vs challenge5 的核心差异

两者共享相同的 startSession/stopSession/sendClientEvent 骨架与 UI，差异集中在数据通道的消息处理与 session.update 内容：

维度 challenge4 challenge5
session.update tools 仅 instructions instructions + tools: REALTIME_TOOLS
conversation.item.created 处理 空处理器（const output = event 后未使用） 检测 output?.type === 'function_call' 并执行 handleToolCall
语音内工具 无 search_location → /api/search_location
常量 无 REALTIME_TOOLS 新增 REALTIME_TOOLS

challenge4 的语音模式只做"听→答"的语音问答，数据通道收到 conversation.item.created 时不产生任何动作；challenge5 让模型能在说话中触发 search_location：当收到 conversation.item.created 事件、且其 type === 'function_call' 时，handleToolCall 执行工具并把结果以 function_call_output 事件写回，再强制 response.create 让模型基于结果继续作答。

handleToolCall：语音内工具调用（challenge5）

handleToolCall(output) 是 challenge5 新增的处理函数（challenge5/frontend/components/voice-mode.tsx#L137-L170）：

  1. 从事件载荷取出 output.name 与 output.arguments，打印到控制台。
  2. 预置一个 ToolCallOutput：response: "Tool call <name> executed successfully."。
  3. 若 toolCall.name === 'search_location'，把 toolCall.arguments 作为请求体 POST /api/search_location，取回 results 并塞进 toolCallOutput.search_results（复用文本链路同一个 SerpAPI 搜索路由）。
  4. 发送 conversation.item.create，写入 { type: 'function_call_output', call_id: output.call_id, output: JSON.stringify(toolCallOutput) } —— 把工具结果作为对话 item 追加。
  5. 发送 response.create 强制模型再生成一轮，保证模型在拿到工具结果后立即回复，而不是停在等待态（源码注释："Force a model response to make sure it responds after tool calls"）。

这一闭环与文本链路的工具循环（lib/tools.ts 的 handleTool）形态一致，但运行在 Realtime 事件协议上：模型发 function_call → 前端执行搜索 → 回写 function_call_output → response.create 续答。

stopSession：资源清理

stopSession()（challenge4/5 一致，见 challenge5/frontend/components/voice-mode.tsx#L100-L117）逆序释放资源：

  • dataChannel.close() 关数据通道。
  • peerConnection.current.close() 关对等连接。
  • 复位状态：setIsSessionStarted(false)、setIsSessionActive(false)、setDataChannel(null)、peerConnection.current = null。
  • 停止本机音频：audioStream.getTracks().forEach(track => track.stop())，setAudioStream(null)、audioTransceiver.current = null。

关闭数据通道与对等连接即释放 WebRTC 传输通道，停止本地音频 track 释放麦克风。tracks（RTCRtpSender[]）与 audioTransceiver 这两个 ref 在源码中被声明并（部分）赋值，但未在 stopSession 里反向移除 sender，麦克风的实际释放依赖 audioStream.getTracks().forEach(=> stop()) 这一条路径。

数据通道事件协议（oai-events）

oai-events 通道承载 Realtime API 的结构化 JSON 事件，出站与入站两类：

  • 出站（sendClientEvent）：
    • session.update（含 instructions 与 challenge5 的 tools）；
    • conversation.item.create（challenge5 写入 function_call_output）；
    • response.create（challenge5 工具调用后强制续答）。
  • 入站（message 监听）：
    • conversation.item.created（模型产出 item 时推送；challenge5 据此识别 function_call）。

音频走 WebRTC 的 RTP 媒体轨道（ontrack/addTrack），不经过数据通道；数据通道只负责控制与结构化事件。

配置与运维要点

  • 语音链路只依赖 OPENAI_API_KEY（/api/session 用 process.env.OPENAI_API_KEY 请求分发 token）与 SERPAPI_API_KEY（challenge5 的语音工具调用经 /api/search_location 读取）。/api/session 是切换点：它把 OPENAI_API_KEY 留在服务端，仅在响应里回传短时间内有效的 client_secret.value 给浏览器，避免主密钥暴露。
  • 正确模型/音色不匹配、缺 SERPAPI_API_KEY、或 offer 携带非法 token 都会使 startSession 失败并落入 console.error；/api/session 自身失败返回 { error } + HTTP 500。
  • challenge4/5 的 python-backend 均无语音对应端点——语音完全由前端直连 Realtime API 完成，Flask 只是文本/工具路径的替代实现。

流式响应（SSE）协议

challenge5 把 challenge1-3 的"一次请求、一次性 JSON 响应"重构为 SSE（Server-Sent Events）流式：后端不再等到整个回答或整个工具调用参数生成完毕才返回，而是通过 text/event-stream 持续向前端推送自描述的增量事件，前端按事件类型逐块原地更新 UI，实现打字机式的文本与实时的工具参数预览。本文聚焦流式协议本身：事件结构、SSE 帧编码、后端如何把 OpenAI 增量重映射为这些事件、前端如何增量读取与处理部分 JSON，以及流模式与非流模式的对比。

该页是 /openwiki/workflows/chat-turn.md（单次回合整体数据流）与 /openwiki/architecture/api-routes.md（路由级对照）中 SSE 细节的展开，重点落在"线路上到底跑了什么、前端如何解析"。

事件与帧编码规范

后端把 OpenAI 的增量 delta 重映射为三种前端事件，每条记录以 SSE 标准帧 data: <json>\n\n 编码（\n\n 为帧分隔符）。协议不依赖字段顺序，前端只需按 event 分派。

事件 触发条件 payload.data 内容 前端语义
assistant_delta delta.content 存在 { content }（文本增量） 累加形成打字机文本
function_arguments_delta delta.tool_calls 存在 { callId, name, arguments }（当块增量参数） 累积参数并实时预览
function_arguments_done finishReason === 'tool_calls' 且正在收集 { callId, name, arguments }（累积完整参数） 触发工具执行
[DONE] 前端终止标记 无 JSON 结束读取循环

四个事件中，assistant_delta、function_arguments_delta、function_arguments_done 由后端发送（见 challenge5/frontend/app/api/get_response/route.ts#L33-L79）；[DONE] 是前端解析时识别的终止标记（challenge5/frontend/lib/assistant.ts#L62-L65），后端路由本身在流迭代完之后直接 controller.close()，并不会显式写出 [DONE]——OpenAI SDK 的流迭代 for await 自然结束即关闭流。

后端：用 ReadableStream 构造 SSE 响应

app/api/get_response/route.ts 的 POST handler 先 await request.json() 取出 { messages }，随后用一个 ReadableStream 作为响应体。流的 start(controller) 内部：

  1. 发起 OpenAI 流式补全：openai.beta.chat.completions.stream({ model: 'gpt-4o', messages, tools })（tools 来自 lib/tools.ts 的 search_location 与 plan_itinerary）。此 API 返回一个可 for await 迭代的异步迭代器，按增量产出 part。
  2. 为工具调用累积状态：路由维护四个模块级局部变量——functionArguments（累积参数串）、callId（调用 id）、functionName（工具名）、isCollectingFunctionArgs（是否处于工具参数收集阶段），用于把 OpenAI 的多个 tool_calls 增量聚合成一次 function_arguments_done。
  3. 逐 part 重映射：每条 part.choices[0].delta 与 finish_reason 决定发送哪类事件，controller.enqueue(\data: ${json}\n\n`)` 把编码后的帧推入流。
  4. 流结束：for await 结束后 controller.close()；start 内部 catch 到异常时 controller.error(error) 终止流。

响应本身用 new Response(stream, { headers }) 返回，Content-Type: text/event-stream、Cache-Control: no-cache、Connection: keep-alive（challenge5/frontend/app/api/get_response/route.ts#L90-L96）。外层 POST handler 的 catch 返回 { error: message } + HTTP 500。

事件重映射的逐条逻辑（challenge5/frontend/app/api/get_response/route.ts#L29-L80）：

  • assistant_delta：delta.content 为真时，把整个 delta 对象序列化进 data 字段推流。
  • function_arguments_delta：delta.tool_calls 为真时，先置 isCollectingFunctionArgs = true，若该块带 id 则记录 callId，若带 function.name 则记录 functionName，并把 delta.tool_calls[0].function?.arguments || '' 追加进累积变量 functionArguments；随后把 { callId, name, arguments: <当前块增量> } 推流。注意 data.arguments 是"当块增量"而非完整参数，完整参数由前端自己累加。
  • function_arguments_done：当 finishReason === 'tool_calls' 且 isCollectingFunctionArgs 为真时，把 { callId, name, arguments: functionArguments }（此时是完整累积参数）推流，然后重置 functionArguments、functionName、isCollectingFunctionArgs，为下一条工具调用做准备。

前端：handleTurn 增量读取

lib/assistant.ts 的 handleTurn(messages, onMessage) 负责消费这条 SSE 流（challenge5/frontend/lib/assistant.ts#L25-L83）：

  1. fetch('/api/get_response', { method: 'POST', headers: { 'Content-Type': 'application/json' }, body: JSON.stringify({ messages }) }) 发起请求（默认走 Next.js 路由；旁边注释的 http://localhost:8000/get_response 是切换 Flask 后端的备选）。
  2. const reader = response.body!.getReader() 拿到 ReadableStream 的读取器，配 new TextDecoder() 逐块解码字节。
  3. while (!done) 循环里 await reader.read()，decoder.decode(value) 得到本块的字符串并追加进 buffer。
  4. 按帧切分：buffer.split('\n\n') 得到多个完整 SSE 帧，把可能是不完整帧的末段 lines.pop() 回 buffer 留待下块拼接（这是处理"一条事件被跨块截断"的关键不变量）。
  5. 对每个完整行，若以 data: 开头则 line.slice(6) 取出 payload：若是 [DONE] 置 done = true 并跳出；否则 JSON.parse(dataStr) 后回调 onMessage(data)。
  6. buffer 余量处理：循环结束后，若 buffer 里仍残留一条完整的 data: 帧（例如流恰好在帧边界结束），再解析一次，避免丢尾。

前端：按事件类型增量更新（processMessages）

processMessages()（challenge5/frontend/lib/assistant.ts#L85-L241）从 store 取快照、组装 [system(SYSTEM_PROMPT), ...conversationItems] 后调用 handleTurn，在 onMessage 里按 event 分派：

  • assistant_delta：assistantMessageContent += data.content，并把 chatMessages 末尾的 assistant message 就地更新（产生打字机逐字追加效果），同时同步更新 conversationItems 末尾的 assistant 消息。
  • function_arguments_delta：functionArguments += data.arguments 累积增量参数，再用 parse(functionArguments) 生成 parsedFunctionArguments（见下节），就地更新 chatMessages 末尾同 callId 的 function_call 条目，并同步 conversationItems 的 tool_calls[0].function.arguments。
  • function_arguments_done：调用 handleTool(data.name, parse(functionArguments)) 执行工具（search_location → /api/search_location、plan_itinerary → /api/create_itinerary），把 function_call 置为 completed 并写入 output，向 conversationItems push { role: 'tool', tool_call_id: data.callId, content: JSON.stringify(result) }，最后递归调用 processMessages() 开启下一个回合，让模型基于工具结果继续作答。

组件层 components/tool-call.tsx 用 SyntaxHighlighter 渲染 functionCall.parsedArguments（即 partial-json 的实时解析结果），用户可看到参数随着流式推送逐渐成形。

partial-json：容错解析部分 JSON

包 partial-json（^0.1.7，见 package.json 依赖）在 lib/assistant.ts 顶部以 import { parse } from 'partial-json' 引入。与标准 JSON.parse 不同，它对截断的 JSON 输入容错：当工具参数尚未完整到达（流式增量中间态，例如 {"locati 或 {"location":"Paris","）时也能返回一个尽量完整的对象，而不是抛 SyntaxError。这使 parsedFunctionArguments 能随每个 function_arguments_delta 实时更新，支撑"工具参数边生成边预览"的体验。真正执行工具时（function_arguments_done 分支）参数已完整，仍用同一个 parse 得到完整对象交给 handleTool。

流模式 vs 非流模式对比

challenge1-3 的 handleTurn 是非流式：await response.json() 一次性拿到完整的单条 assistant MessageItem，然后整体 push 进 chatMessages 与 conversationItems（见 challenge1/frontend/lib/assistant.ts#L55-L65）。challenge5 改为流式后，两条路径的差异如下：

维度 非流式（challenge1-3） 流式 SSE（challenge5）
后端 一次性返回完整 JSON text/event-stream 持续推进增量事件
前端读取 await response.json() 一次完成 getReader() + TextDecoder 增量读
文本展示 等到全部生成后一次性出现 打字机式逐字追加
工具参数 完整后可见 边生成边预览（partial-json）
首字节延迟 高（等待完整回答） 低（首个增量即可渲染）
中断/错误 整体失败或整体成功 可在帧边界增量处理，controller.error 终止流
实现复杂度 低 中（需按帧切分、处理部分 JSON）

流式的主要收益是感知延迟降低（首块输出即可上屏，而非等待完整回答）与工具调用可视化（参数实时成形）；代价是协议解析复杂度上升（SSE 帧切分、跨块缓冲、部分 JSON 容错）。非流式更简单可靠，但对长回答与长参数缺少渐进反馈。Flask 后端（python-backend/app.py 的 /get_response）仍是非流式——若前端切换到该后端，handleTurn 的 SSE 解析逻辑需同步改为直接 response.json()。

函数调用（工具调用）流程

Wanderlust Concierge 是旅行助手系统，模型并不能直接访问外部的酒店/景点搜索或自动规划行程——它必须通过声明好的工具把这类需求"外包"给后端路由执行。本文梳理从模型决定调用工具、到工具结果作为 tool 角色消息回送给模型、再到模型据此生成最终回复的完整循环。

整个循环横跨三层：

  • 工具 Schema（lib/tools.ts）：向前端与后端共同声明的函数定义，决定模型能调用哪些工具及其参数形态。
  • 后端路由（app/api/...）：真正执行工具的落点，search_location 查 SerpAPI，plan_itinerary 用推理模型规划行程。
  • 前端编排（lib/assistant.ts + lib/tools.ts 的 handleTool）：把模型返回的 tool_calls 翻译为对后端的 HTTP 调用，再把结果以 role: 'tool' 消息写回消息数组，最后递归重启一轮对话。

仓库里对"一次工具调用循环"有两种建模：challenge1-3 是非流式（handleTurn 递归），challenge5 是 SSE 流式（processMessages 递归）。二者共享同一套工具 Schema 与后端，区别只在结果回填的驱动方式。本文以 challenge5 流式为主线，并与非流式对比。

工具 Schema：Search_location 与 plan_itinerary

challenge5/frontend/lib/tools.ts 导出两个关键量：

  • handleTool(toolName, parameters)：工具分派器。按 toolName 分支，构建对后端路由的 fetch（POST）并返回解析后的 JSON 结果。
  • tools：传给 OpenAI 的函数 Schema 数组。

tools 数组声明了两个 type: 'function' 工具：

  1. search_location —— 在给定地点搜索地标或酒店。参数对象 { location, search_query }（location 形如 City, (State), Country；search_query 例如 "boutique hotels"），两者均 required，且 additionalProperties: false、strict: true（严格模式）。handleTool 解构出 { location, search_query } 后 POST 到 /api/search_location（见 challenge5/frontend/lib/tools.ts#L32-L57 与 #L1-L16）。
  2. plan_itinerary —— 用 stops 参数规划行程。参数是 stops 数组，每项含 { location, duration(天数), type(游览类型), participants(人数) }（均 required）。handleTool 用 JSON.parse(parameters) 解析出 stops 后 POST 到 /api/create_itinerary（见 challenge5/frontend/lib/tools.ts#L58-L95 与 #L17-L29）。

同一个 tools 数组在非流式的 challenge2 前端（challenge2/frontend/lib/tools.ts）与 Python 后端（challenge2/python-backend/app.py#L16-L42）中也以相同形态定义（早期版本只有 search_location，plan_itinerary 是后加入的）。

前端 get_response 路由把 tools 交给模型

/api/get_response 路由（challenge5/frontend/app/api/get_response/route.ts）是工具循环的触发点，它在调用 OpenAI 时显式传入 tools 数组，模型据此才可能返回 tool_calls：

const openaiStream = openai.beta.chat.completions.stream({
  model: 'gpt-4o',
  messages,
  tools: tools as ChatCompletionTool[]
})

请求体里的 messages 就是前端组装的 [system(SYSTEM_PROMPT), ...conversationItems]，其中 SYSTEM_PROMPT（lib/constants.ts）明确提示模型："当合适时可使用 search_location 工具搜索地标或酒店"。由于模型被喂了工具 Schema，它在合适的时机返回的增量 delta 里会出现 delta.tool_calls，从而触发后续的工具执行分支。非流式版本（challenge2-4）则用 openai.chat.completions.create({ ..., tools })（见 challenge2/frontend/app/api/get_response/route.ts#L13-L18），一次性得到带 message.tool_calls 的完整返回。

流式模式：事件累积、执行、递归

challenge5 在 processMessages 的回调里按事件类型驱动整条工具循环（challenge5/frontend/lib/assistant.ts#L104-L241）：

  • function_arguments_delta：每收到一个增量块，执行 functionArguments += data.arguments 累积流式参数；同时更新 UI 上的 function_call 气泡（status: 'in_progress'）和 conversationItems 中 assistant 消息的 tool_calls[0].function.arguments。
  • function_arguments_done：当 finishReason === 'tool_calls' 时路由发出该事件，携带累积完整的 arguments。前端随即调用 handleTool(data.name, parse(functionArguments)) 执行工具。
  • 结果回填：把返回结果以 role: 'tool' 消息 push 进 conversationItems（{ role: 'tool', tool_call_id: data.callId, content: JSON.stringify(toolCallResult) }），并把 function_call 气泡标记为 status: 'completed'、写 output。
  • 递归：最后 await processMessages() 重新组装含 SYSTEM_PROMPT 与最新 conversationItems（含 tool 结果）的消息数组，再发一轮 /api/get_response，让模型基于工具结果生成最终回复。当模型不再返回工具调用而是正常文本时，assistant_delta 分支接管输出，回合结束。

后端路由（challenge5/frontend/app/api/get_response/route.ts#L24-L79）在流内自行维护 functionArguments / callId / functionName / isCollectingFunctionArgs 四个局部状态来累积参数，并在 finishReason === 'tool_calls' 且正在收集时发出 function_arguments_done，随后重置这些累积状态以备下一轮工具调用。

非流式模式：handleTurn 递归

challenge2-4 没有 SSE，handleTurn 在收到完整 JSON 回复后检测工具调用（challenge2/frontend/lib/assistant.ts#L56-L87）：

  1. 把返回的 assistant 消息 push 进 conversationItems。
  2. 检查最后一条消息：lastMessage.role === 'assistant' && lastMessage.tool_calls && lastMessage.tool_calls.length > 0，若成立则进入工具分支。
  3. 调用 handleTool(lastMessage.tool_calls[0].function.name, lastMessage.tool_calls[0].function.arguments)，把返回结果以 role: 'tool' 消息（含 tool_call_id）push 进 conversationItems。
  4. await handleTurn() 递归重启——handleTurn 自己从 store 取快照并重新组装消息数组，再发一轮请求，直到模型不再返回工具调用，此时才把 assistant 消息 push 进 chatMessages 并结束。

注意此处 handleTool 收到的是原始 arguments JSON 字符串，在 JSON.parse(parameters) 后取字段（challenge2/frontend/lib/tools.ts#L4），与流式模式下前端已 parse 过不同。

工具后端路由

工具执行最终落到两个后端路由，它们的职责就是真正访问外部服务或推理：

/api/search_location（challenge5/frontend/app/api/search_location/route.ts）——查 SerpAPI：

  • 从请求体取 { location, search_query }。
  • 读取 process.env.SERPAPI_API_KEY，若缺失则 throw new Error('SERPAPI_API_KEY is not defined')，被 catch 后返回 { error } 与 HTTP 500。
  • 用 getJson({ engine: 'google', q: search_query, location, api_key: serpApiKey, limit: 5 }) 查询 Google organic results（limit: 5），返回 response.organic_results 数组。Python 后端（challenge2/python-backend/app.py#L62-L83）用等价逻辑（GoogleSearch(params).get_dict()["organic_results"]）。

/api/create_itinerary（challenge5/frontend/app/api/create_itinerary/route.ts）——规划行程：

  • 从请求体取 stops。
  • 用 model: 'o1'（推理模型） 调用 openai.chat.completions.create，消息为 [{ role: 'system', content: ITINERARY_PROMPT }, { role: 'user', content: JSON.stringify(stops) }]。
  • ITINERARY_PROMPT（lib/constants.ts）指导模型按停留时长、游览类型、参与人数规划，并基于"最便利的旅行顺序"给出最优行程顺序与离开时间建议。
  • 返回 { itinerary: response.choices[0].message.content }；出错返回 500。

关键边界与失败语义

  • 密钥缺失：search_location 无 SERPAPI_API_KEY 时抛错返回 500，handleTool 拿到的 data 是 { error } 而非搜索结果，会原样作为工具 result 写回模型。
  • 递归终止条件：循环依赖"模型不再返回 tool_calls"。只要模型继续要工具结果，processMessages/handleTurn 就会持续递归；一旦模型产出普通文本，就走 assistant_delta/push 分支结束回合。
  • 并行双数组一致性：chatMessages（UI 渲染）与 conversationItems（发给 API）在每次工具事件中同步更新；工具结果只写入 conversationItems（role: 'tool'），UI 侧则通过 function_call 气泡的 status/output 反映。
  • 后端可切换：工具与对话请求注释里都保留了 http://localhost:8000/... 的 Python（Flask）后端备选，替换即可在 TS Next.js 路由与 Flask 后端间切换。
